# Pi in Container · `pc` / `pi-container`

在容器中运行原生 [Pi Coding Agent](https://github.com/earendil-works/pi)，通过 tmux 托管 Pi 进程，断开终端后接回同一进程，并管理开发容器与独立服务容器。宿主无需安装 Node.js 或 Pi。

项目仓库：[L4nterns/pi-container](https://github.com/L4nterns/pi-container)。Gateway 在公开仓库 [L4nterns/pi-provider-gateway](https://github.com/L4nterns/pi-provider-gateway) 独立维护，通过网络安装，不捆绑在本项目源码或镜像中。

## 职责与入口

**宿主操作入口为 `pc`，保留完整名称 `pi-container`；两者是同一个交互菜单。** 无参数进入菜单，只额外接受 `-h` / `--help`，不提供子命令或 Pi 参数转发。项目不提供浏览器控制台、管理 HTTP API 或管理网站。

| 负责方 | 职责 |
| --- | --- |
| 原生 `pi` | 对话、`/new`、`/resume`、`/compact`、模型、思考档位、主题、provider 与插件 |
| `pc` / `pi-container` | 项目与服务容器生命周期、托管与接回原进程、应用自启动策略 |

Pi 的 `--resume` / `--continue` 恢复磁盘历史，不是附着到另一个正在运行的 TUI；RPC 是程序控制接口。tmux 管理的是进程与终端连接，不替代 Pi 的对话功能。账号、路由和额度由上游管理。

## 安装

需要 Linux、Bash 4.1+、GNU coreutils、`flock`，以及有权限使用的本机 Docker Engine / Compose v2。「检查更新」另需 Git 2.26+；读取公开仓库不需要 GitHub token。部署功能另需宿主 OpenSSH 客户端。不支持远程 Docker Engine；WSL 使用 Linux 环境。

公开命令为短名 `pc` 和完整名 `pi-container`，不占用 groff 的 `pic` 命令。两者指向同一脚本，没有两套逻辑。安装链接和 Shell PATH 由操作者管理；若宿主已有同名命令，先核对，不自动覆盖。

以下步骤用于**全新安装**，不要覆盖已有 `.env`、配置、凭据或业务数据。本项目提供源码，不提供预构建镜像。

```bash
git clone https://github.com/L4nterns/pi-container.git
cd pi-container

if [ "$(id -u)" = 0 ]; then BIN_DIR=/usr/local/bin; else BIN_DIR="$HOME/.local/bin"; fi
mkdir -p "$BIN_DIR"
ln -s "$PWD/bin/pi-container" "$BIN_DIR/pi-container"
ln -s "$PWD/bin/pc" "$BIN_DIR/pc"
export PATH="$BIN_DIR:$PATH"

mkdir -p ~/projects/demo
cd ~/projects/demo
pc
```

普通用户将 PATH 配置保存在 Shell 启动文件中；也可直接使用源码中的 `bin/pc`。无需先从菜单安装运行环境：选择「启动 Pi」或「项目管理 → 选择项目 → 项目路径 → 管理终端」时，未创建的项目仅在开发镜像缺失时构建，再按需创建／启动开发容器；已有容器直接复用。已有镜像直接复用，不在启动时更新源码或软件。首次构建同样使用 `--pull --no-cache`，不提供手工构建表单。不要把凭据放入 Docker 构建参数或 Dockerfile，它们可能留在构建日志、缓存及镜像元数据中。

部署默认关闭，不必手工创建 `.env`。需要部署时，通过「服务管理 → 部署配置」设置，再明确选择「启动容器」，只准备服务所需的镜像和容器。启动 Pi 或开发 Shell 不会构建、创建、启动或等待服务；手动停止的服务保持停止。服务管理终端使用开发镜像作为独立 SSH 客户端，若服务未运行，会先询问是否启动，Enter 确认、Esc 取消。

源码 tar 包仍可解压后按需准备和卸载运行环境，但没有 `.git` 的安装不能原地检查源码更新。要使用更新功能，应通过 Git clone 建立安装；已有 tar 安装请先备份并按部署文档规划路径与数据迁移，不把新源码直接解压覆盖旧配置或业务目录。

## Gateway 安装与更新

启动托管 Pi 时，入口按 `config/pi-bootstrap.json` 调用原生 `pi install`，安装尚未配置的默认包。Gateway 来源为：

```text
git:github.com/L4nterns/pi-provider-gateway
```

镜像还会安装一个本地工具策略包：

```text
/opt/pic/extensions/tool-policy
```

来源不带版本、tag 或提交 SHA，首次安装获取公开默认分支的当前内容，不需要 GitHub token。安装需要访问 GitHub 与 npm；引导器执行的安装失败时明确报错，不写完成标记，网络恢复后可重试。

包和初始化标记保存在持久化的 `data/` 中。成功初始化后不重复安装；用户卸载已记录的来源后，不自动装回。镜像本地工具策略包也走同一标记与原生包声明。开发 Shell 与接回已有进程都不执行包初始化。

引导器使用 Pi 的原生包路径解析检查已有同名安装，包括本地相对路径、绝对路径、HOME 路径和 file URL。它只读取包元数据，不加载扩展代码、不改写用户包声明、不自动迁移来源。

插件后续更新由原生 Pi 管理。默认 Git 安装可在开发 Shell 中执行：

```bash
pi update git:github.com/L4nterns/pi-provider-gateway
```

更新前协调正在使用该插件的 Pi，再按原生方式重新加载；本项目不在启动时自动升级插件。

进入 Pi 后，使用 `/gateway → 添加服务` 填写服务 ID、URL 和 Key；已有服务通过「管理服务 → 连接配置」设置。连接和目录保存后自动应用；「刷新配置」仅重新读取本地配置与缓存，「同步目录」读取上游模型列表。「查看模型」只读；「编辑模型」提供名称、上下文、最大输出、输入、思考、价格和缓存字段，以及高级 JSON 和协议偏好，保存后自动应用。使用 `/model` 和 `/thinking` 选择模型与思考档位。网关菜单的密钥输入有遮罩；Pi 1.5.0 的原生 `/login` 输入框会明文回显 secret。

## 菜单与活进程

在具体项目目录运行 `pc` 或 `pi-container`：

```text
> 接回 Pi          当前目录，继续原进程
  启动 Pi          当前目录，断开后继续运行
  项目管理         选择项目与批量清理
  服务管理         本安装共享服务
  检查更新         更新源码与运行环境
  卸载             移除运行环境，保留数据

「Esc」退出 · 「↑/↓」选择 · 「Enter」确认
```

不设置「返回／退出」菜单项；主菜单用「Esc」退出，子菜单用「Esc」返回一层。说明列统一对齐，提示、进度和按键说明放在底部；按键提示上方有与标题一致的分隔线。导航和滚动只重画变化的行，不反复清屏。

**项目管理先选择项目，再操作所选项目。**「选择项目」按完整宿主路径列出本安装、当前宿主 UID 的开发容器及状态；长路径用左右键查看。选中后的顺序为 **查看状态 → 管理终端 → 查看日志 → 停止容器 → 删除容器**，操作页显示目标路径。日志、停止和删除始终针对所选容器；容器、标签或挂载变化时要求返回列表重选，不回退到调用目录、不操作替代容器。进入已有容器的 Shell 不解析部署配置、不构建镜像或启动服务；只在需要时启动所选容器，并核对真实目录与容器工作区的设备／inode，拒绝已删除、别名或重新创建后与原挂载不同的目录。

有效的当前目录没有容器时，列表明确显示「未创建」候选；只有选择其管理终端才按需准备，日志、停止和删除置灰。选择、查看、取消不创建资源或租约。项目管理的「批量清理」独立于项目操作，范围始终是**本安装、当前宿主用户的全部开发项目**，不只针对刚选中的项目。

顶层「接回 Pi／启动 Pi」仅针对调用目录。服务管理针对本安装共享服务，不随项目选择变化；在停止前另有「启动容器」，末尾提供「应用自启动」「部署配置」。没有「安装」按钮，也没有手工构建／重建入口：首次需要时仅准备对应环境，显式更新使用根菜单「检查更新」。仅当发现受管资源（或资源状态无法确认）时显示「卸载」，不维护第二份安装登记；项目列表也不新增注册表。

- **查看状态**：以宿主项目路径为一列显示状态，区分未创建、已停止及退出码、运行和健康状态；另列源码、镜像是否待重建／替换，以及运行容器的 Pi 版本和 Gateway 提交。不会把已停止容器误写成不存在；查询不启动容器或更新软件。
- **查看日志**：在结果页查看最近 200 行，去掉含安装标识的容器名前缀。应用原本输出的 JSON 或业务错误保持原样，不按关键词删日志；日志可能含业务信息。
- **批量清理**：选择「仅清理空闲」或「中断后清理全部」，Esc 取消。空闲清理跳过占用／未知项目，结果明确显示已删除、保留／未完成数量；没有容器时提示无需清理。仍有未完成项可再确认中断后清理。挂载数据保留，不删除镜像、不做全局 prune。停止／删除单个项目也先列目标与会话，Enter 明确确认后才中断；已停止或未创建时显示「无需操作」，不冒充执行成功。
- **部署配置**：菜单编辑部署开关、数据目录、HTTP 端口和公网模板，确认后只保存安装目录 `.env`，保留其他配置。已有服务的有效端口或数据目录变化时，随后列出差异与应用／SSH 连接，另行询问「是否重建服务容器」，Enter 确认、Esc 取消；无需手动删除再启动，取消重建也保留已保存的配置。确认重建会中断应用、丢弃容器可写层，但保留挂载数据和脚本；原先停止的服务保持停止，不迁移旧数据。仅改公网模板或禁用部署不重建／停止现有服务；同名宿主环境变量仍优先于 `.env`。详见 [DEPLOYMENT.md](DEPLOYMENT.md)。
- **应用自启动**：逐个应用启用／禁用，确认屏显示应用名、当前策略及启用／禁用目标；用「Esc」取消，默认选中执行项，Enter 提交。它修改持久化 Supervisor `autostart`，下次服务启动生效，当前进程不变。

| 概念 | 含义 |
| --- | --- |
| 运行中的 Pi | 仍存活的进程；没有终端连接时，请求、输出和工具仍可继续执行 |
| 历史对话 | Pi 保存的磁盘数据，不代表进程仍在运行 |
| 终端连接 | 通向进程的一条连接，断开不等于结束 Pi |

- **接回**只连接当前项目已有的开发容器中的指定进程，不启动容器、不初始化插件、不启动或等待可选服务容器，不重放历史或重发模型请求。进入或返回主菜单时，只读检查可接回的 Pi；确认没有时「接回 Pi」置灰，方向键、Home／End 和翻页均跳过，初始焦点移到「启动 Pi」。状态读取失败时保持可选并提示未确认，不能把未知当成无会话；选择时仍重新核对，进程已结束或查询失败时不启动替代进程。
- **启动并托管**创建 Pi 进程，不传入历史选择、模型或思考设置。在 Pi 内可以用 `/new`、`/resume` 切换对话；进程标识不是对话文件标识。
- **断开**：`Ctrl+B`，松开，再按 `D`，回到宿主 Shell，本次菜单结束；也可关闭宿主 SSH 终端。仍存活的托管进程继续执行。
- **结束**：接回后在原生 Pi 中使用 `/quit`，保留历史。需要中断整个环境时，在项目管理中检查影响并确认停止或删除容器。
- 所有菜单、进程列表和确认框使用 **Esc 返回／取消、↑/↓ 选择、Enter 确认**，不使用数字快捷键，也不设置「取消」列表项。每次进入都默认选中第一个可操作项；更新、删除等确认屏也可直接 Enter 授权，不必先按方向键。禁用项始终跳过。长列表支持 PageUp / PageDown、Home / End。
- 主菜单与子菜单不记忆上次位置，从结果页或内层返回时同样从第一个可操作项开始。状态、日志、构建输出、错误和空列表均留在同一独占屏幕，用「Esc」返回一层；结果页的 Enter 不承担返回功能。确认问题、状态与风险分开展示，影响清单可分页与横向查看；翻页本身不执行操作。标题与内容分层，行数、操作结果和按键提示在底部。
- 进入 Pi 或真实 Shell 时交还终端并结束菜单链。Shell `exit`、Pi 退出／断开均回到调用 `pc` 的宿主 Shell，不再弹回多层菜单。进入终端失败时也直接保留原错误与退出码，不静默回菜单。服务管理终端的启动询问发生在交接之前，取消不会交接或启动服务。普通启动、停止、自启动策略等菜单操作仍可返回并显示底部反馈。
- 构建、创建容器和更新操作实时显示命令输出尾部、经过时间与输出字节数；这些只说明命令尚在执行，不是完成比例。执行期间 Esc 不离开，Ctrl+C 中断并等待子进程组收敛，再显示结果。日志捕获在磁盘上仅保留当前／上一段，合计最多 1 MiB，结果页显示末尾最多 5000 行；私有临时捕获在返回或可处理信号后删除，不留长期转录。Docker daemon 已接收的任务可能继续，失败／中断后须核对实际资源状态。
- 菜单需要至少 6 行、12 列的 ANSI / UTF-8 交互终端，不接受管道输入。有目标／风险正文的菜单至少需 8 行，并始终预留可分页的正文行；6／7 行时只显示放大提示，Enter 不授权，放大后恢复第一项选择，Esc 仍可取消。进入 Pi 或 Shell 时恢复终端输入模式、光标和主屏；宿主不需要 Node、Pi 或额外菜单程序。

### 输出过程中断开与接回

1. 在 Pi 中提交任务。
2. 输出或工具仍在进行时，用 `Ctrl+B d` 断开。
3. 再次进入宿主同一项目目录，运行 `pi-container`。
4. 选择「接回 Pi」并选中原进程。

多个终端连接同一进程时共享输入和显示，不是隔离观察者，应避免同时输入。tmux 保存终端状态和有限滚屏，不是完整日志或任务检查点，也不能修复上游断流。

Pi 退出、崩溃或容器 / 宿主重启后，原执行状态消失。可启动新 Pi，再用原生 `/resume` 选择历史，但不能复活旧请求和工具。直接在开发 Shell 中运行 `pi` 不经过托管，不承诺断开后继续运行。

最后一个真实运行的 Pi 结束，并且宿主终端租约、开发 Shell、外部 Docker exec 均为空时，自动停止当前项目的开发容器。断开不算结束 Pi；只要后台还有 Pi 就不停止。除终端退出时立即检查，启动／接回会启动一个按项目与容器 ID 单例的宿主 Bash 空闲观察器，每两秒检查一次，覆盖后台最后一个 Pi 自行结束；旧容器被替换、删除或停止时观察器退出，不会停止替换后的新容器。它不启动任何软件或服务，不管理对话、不挂载 Docker socket；只保留最新一次诊断，不留长期转录。读取状态失败或未知时不自动强停。宿主强杀观察器或清理用户进程后，需再次通过菜单接回／启动来恢复观察；不承诺被强杀后仍有宿主后台管理。

## 终端编码、颜色与主题

托管环境使用 Debian 的 `C.UTF-8`，宿主终端需支持 UTF-8 并提供中文字形。

镜像内 tmux 3.5+ 使用 `extended-keys on` 与 `extended-keys-format csi-u`，让 Pi 按原生协议区分 Enter 与 Shift+Enter；不强制外层终端支持它没有的能力。整条终端链仍须能转发组合键，不能换行时可用原生 Ctrl+J。若出现 `tmux extended-keys is off`，说明当前 tmux server 尚未启用此配置，不影响模型或工具执行，但 Shift+Enter 可能被当作提交。

配置随开发镜像更新，不会自动重启已有 tmux server 或 Pi；不要为消除警告运行 `tmux kill-server`，它会结束该 server 下的全部会话。非项目管理的 tmux 需在对应层单独配置，参见 Pi 的 [tmux 说明](https://github.com/earendil-works/pi/blob/main/packages/coding-agent/docs/tmux.md)。

终端连接显式传递宿主的 `TERM`、`COLORTERM` 和 `COLORFGBG`，避免 Docker 的默认 `TERM=xterm` 让 tmux 把灰阶、256 色和 RGB 压成 8 种基础色。镜像提供 `ncurses-term` 终端描述数据；宿主应如实设置终端类型，非标准类型需要对应的 terminfo。

只有 `COLORTERM=truecolor` 或 `24bit` 明确声明真彩色时，辅助程序才向 tmux 声明 RGB；否则由 TERM / terminfo 决定颜色能力，不一律强制真彩色。

**Pi 主题由原生 `/settings → Theme` 管理。** 默认 `system` 跟随终端调色板；也可自行选择 `dark`、`light` 或主题对。项目不强制深色主题、不重写颜色、不修改用户主题设置。不同终端的 ANSI 调色板及透明背景仍可能带来视觉差异。

接回时 tmux 按当前客户端能力绘制；Pi 自身缓存的主题和能力由原生功能管理。需要改变 Pi 设置时使用 `/settings` / `/reload`；需要重启进程时先保存工作并正常退出，不为调整颜色自动结束任务。

## 容器、权限与数据

远程使用先通过已有 SSH 登录宿主，再在项目目录运行 `pi-container`。宿主操作者必须具有 Docker 权限；Pi 和应用容器不挂 Docker socket，也不开放额外管理端口。

同一安装只使用同一宿主身份。开发进程以非 root 运行；宿主 root 映射到 UID/GID 1000，并通过 ACL 授予工作区访问权。ACL 会持久改变宿主元数据，同机真实 UID 1000 也会得到访问权；这里不是多租户沙箱。详见 [SECURITY.md](SECURITY.md)。

| 位置 | 内容 |
| --- | --- |
| 项目目录 | 挂载为 `/workspace` 的开发文件 |
| `data/` | Pi 配置、凭据、扩展及 `project-history/` 中按项目保存的对话 |
| `.runtime/` | 宿主项目锁和终端连接租约 |
| `.deploy-keys/` | 可选部署管理身份 |
| `services-data/` 或配置的外部目录 | 可选服务持久化数据 |

开发容器身份由安装路径、宿主 UID 和项目路径派生，运行时位于 `/opt/pic`。项目不自动接管其他安装的容器或迁移历史目录。移动安装或切换身份前，应停止相关容器、备份并明确处理数据，避免并行写同一份持久状态。

部署使用独立 Debian 服务容器和标准 SSH/SFTP。服务 SSH 终端不挂载项目或 Pi 数据，也不启动开发容器。服务默认 `restart: unless-stopped`，新应用默认 `autostart=true` / `autorestart=true`，已有禁用策略不变；宿主 Docker 须开机启动，手动停止后需手动恢复。`pc → 服务管理 → 应用自启动` 管理下次恢复策略，不中断当前应用。配置、发布和备份见 [DEPLOYMENT.md](DEPLOYMENT.md)。停止或重建服务会中断应用；删除容器不删除 bind 数据，不保证零停机。

## 检查更新与卸载

「检查更新」更新宿主源码、两种镜像及已有受管容器。只在用户主动选择时访问固定公开仓库的 `main`，不在启动时拉取，不修改本地 origin，也不请求 PAT。

1. 显示版本、范围数量和活动 Pi／终端／应用，不列开发项目路径或无活动的容器状态。清单为当前快照；确认涵盖范围内全部会话，包括后台、新连接及状态未知的连接。Esc 取消，执行项默认选中，Enter 确认。
2. 本地修改、非 main／分叉提交或游离 HEAD 时，先询问是否备份：原提交保留在 `pc-backup-*` 分支，源码修改和未跟踪源码保留在本地 Git stash，切换到上游 main，不自动重放。`.env`、会话和应用数据不进入该备份。失败后可用原生 Git 检查分支和 stash，不自动丢弃或回灌备份。
3. 确认后更新源码，以 **`--pull --no-cache`** 重建开发、服务两种镜像；两者都成功才替换容器。不会执行全局镜像／缓存清理。Pi 依赖使用构建时 npm `latest`，不是启动时更新。
4. 仅重建已有受管容器。重建会销毁 Pi 的原进程及容器可写层，不自动重启 Pi、恢复历史或重发请求；开发容器重建后保持停止，下次按需启动。原先运行的服务重建并等待核心健康，原先停止或状态未知的服务不启动。应用恢复依赖持久化部署脚本，不保证零停机。
5. 源码、镜像、多个容器之间不是原子事务；失败保留真实错误和已完成步骤，不自动回滚。即使源码已是最新，仍可确认重新构建和重建以重试失败步骤或更新镜像依赖。执行后仍停留在结果页；Esc 返回主菜单并重新加载当前宿主源码，成功或失败都不退出菜单、不继续执行旧版本的菜单代码。

根菜单 **卸载** 由实际受管容器、镜像及本安装标签判断，不维护第二份安装登记。卸载先列进行中的会话，再询问是否中断；明确确认后删除本安装、当前用户的开发容器、共享服务容器、受管镜像及可删除网络。保留 `data/`、`.env`、`.deploy-keys/`、应用持久目录及其中的部署脚本，也保留源码和 `pc` 入口，下次使用相应功能时按需准备环境。**容器可写层不保留。** 不带 `--volumes`，不做全局 prune；有范围外引用的共享镜像／网络不强删并保留诊断。无法可靠归属本安装的历史无标签悬空镜像不擅自删除。

Gateway 安装在持久化 `data/`，不随更新、重建或卸载运行环境而更新／删除；插件更新仍由原生 Pi 在开发 Shell 执行 `pi update git:github.com/L4nterns/pi-provider-gateway`，然后 `/reload` 或正常重启。实际 Pi 版本由构建时 npm registry 决定，不承诺任意未来版本兼容。

## Shell 执行边界

开发镜像把工具策略扩展放在 `/opt/pic/extensions/tool-policy`，由启动引导器按 `config/pi-bootstrap.json` 的原生 `pi install` 安装并加载：

- `bash` / `powershell` 未显式给 `timeout` 时使用 **120 秒**；显式值超过 **600 秒** 会提示长任务，超过 **3600 秒** 会限制到硬上限。
- 工具运行时在 footer 显示已运行时间与无输出时长，长时间静默不再看起来像卡死。
- 该扩展只限制单次工具执行，不做模型或 provider fallback；失败后的重试仍由 Pi 负责，账号/供应商切换仍属于上游中转（例如 Magpie）。

容器首次启动时，如果 `$PI_CODING_AGENT_DIR/AGENTS.md` 不存在，会从 `/opt/pic/config/AGENTS.md` 写入一份环境规则，重点包括：不要把 `git grep` 用在 blobless/partial clone 上（会触发 lazy blob fetch 并长时间无输出），网络命令要设置超时。已有 `AGENTS.md` 不会被覆盖。
