# Application deployment and operations

Read `/opt/pic/DEPLOYMENT.md` before acting. Connect using `ssh app-services`; transfer reviewed artifacts with `sftp app-services` or `scp`. All projects in this installation share management access. Inspect existing applications before choosing names or changing shared dependencies.

The service is a Debian environment, not a language-specific deployment platform. Inspect installed tools and install the runtime and system dependencies the application actually requires. Container administration and application execution are different roles: never run the application as root. Never request Docker socket access or modify host services.

Record repeatable environment preparation in the persistent service directory; an interactive installation alone does not survive container recreation. The administrator HOME `/home/deploy` is disposable staging, not automatically durable state. Persist only identified application data, reviewed runtime artifacts, required configuration and identities; restore reproducible dependencies from setup scripts. Keep application artifacts, persistent business data, supervisor definitions and gateway configuration separate. Do not upload repositories wholesale, credentials, development configuration or unrelated files.

Use Supervisord for foreground applications and crash recovery. New applications default to `autostart=true` and `autorestart=true`; preserve an existing disabled policy unless the user asks to enable it. Use one stable `[program:<name>]` per application in root-owned, non-group/world-writable `/srv/app-services/supervisor/*.conf`. Never include `sshd` or `nginx` in application definitions. The host `pc` / `pi-container → 服务管理 → 应用自启动` menu edits this same native `autostart` field: no second registry, no current process restart, effect on next service/Supervisor startup. Do not overwrite that policy when updating an application. `sudo deploy-apps list` shows policy and revision; `sudo deploy-apps set <name> <true|false> <revision>` is the equivalent service-side operation. It is not a host subcommand.

Temporary stop, persistent policy and unpublishing are separate operations. `supervisorctl stop <name>` alone does not survive restart. To keep an app stopped, persist `autostart=false` first, then explicitly stop only the authorized application and remove its route after validating Nginx. The policy helper deliberately does not reread/update: `supervisorctl update` may restart a changed program; only run a targeted update when that interruption is intended. Re-enabling policy does not start the app now; use an explicit start after checking dependencies, then restore the route after health checks. The service container uses `restart: unless-stopped`; manually stopped containers stay stopped, including when a new Pi or development shell starts. Host settings are available in `pc → 服务管理 → 部署配置`; saving them alone does not start, stop, recreate or migrate a service. If an existing service needs a changed port or data mount, the host menu separately lists differences, applications and connections and asks for explicit rebuild consent; Enter authorizes the selected action and Esc cancels. Rebuilding interrupts applications/SSH and discards the container writable layer: recovery depends on persistent setup scripts and data, not on container state. Old data is not moved to a new directory. A previously stopped service remains stopped after a settings rebuild. If the service is stopped or absent, ask the operator to explicitly start it in that menu; never request Docker access inside the development container. An existing development container created without deployment access is not replaced automatically: the operator must finish its sessions, explicitly remove it and start it again after the service is running. Docker must start on host boot. Reboot interrupts current connections and requests; recovery is not zero downtime.

Use the reviewed examples in `examples/python/` as a starting point, adapting name, fixed UID, port and runtime; they do not limit supported application languages. The administrator has unrestricted container sudo; never confuse that with the permissions of application processes. Coordinate changes to shared Supervisor configuration using `sudo flock /run/app-services/change.lock ...`, as the policy helper does. This is a cooperation lock, not an authorization boundary. Validate gateway configuration before reload, then check that requests reach the intended application. Internal health is not public verification; if a public URL is configured, inspect HTTPS, assets and business endpoints too. Do not claim zero downtime or automatic database rollback.

Stopping preserves application data. Permanent deletion requires explicit user authorization and an appropriate backup; identify and remove only the selected application's processes, definitions, files and account. Do not erase shared configuration or other applications. Never disclose SSH keys, tokens, application secrets or raw private logs.
